# retail-rag-assistant
# 超市商品智能客服（RAG 增强）
针对商品知识多源分散、查询同时存在精确匹配与语义匹配、价格库存等信息持续变化、无答案问题易被强行回答等问题，构建基于 RAG 的智能客服系统，实现多源知识接入、增量索引、混合检索、质量门禁与离线评测，支持商品咨询、条件推荐、促销活动与售后政策问答，适用于零售客服与知识检索可靠性验证场景。

系统聚焦的问题不是"怎么让 LLM 回答得更聪明"，而是：**商品知识多来源、经常变化，系统怎样稳定地找对知识，并把经过质量检查的内容交给 LLM**。

## 🎯 项目背景

传统零售客服 RAG 系统面临四大核心痛点：

| 痛点 | 表现 | 本系统解决方案 |
|---|---|---|
| 知识来源分散 | 商品说明、FAQ、售后政策分散在多格式文件，促销上新频繁 | 多格式解析与表格抽取 + manifest 增量索引 + 三级去重 |
| 精确与语义并存 | 品牌/规格/SKU 需精确匹配，口语表达需语义理解 | 规则+LLM 双层约束提取，BM25+向量双路召回，RRF 融合 + CrossEncoder 重排 |
| 信息频繁变化 | 价格、库存、促销有效期持续变化，旧数据干扰回答 | 结构化目录确定性回答 + 过期促销剔除 + 新鲜度加成 |
| 检索质量不可验证 | 无答案问题被强行回答，检索优化无度量依据 | 三信号质量门禁 + 85 条人工标注集五模式消融评测 |

## ✨ 核心特性

### 🔍 智能检索引擎

- **语义级切分**：段落优先 + 标点分句 + 块重叠（500 字块 / 80 字重叠），避免固定长度切分造成的语义断裂
- **混合检索**：BM25 关键词检索 + 向量语义检索，RRF 按稳定 `doc_id` 融合去重
- **CrossEncoder 重排**：对 (query, doc) 逐对打分精排，排序阶段引入意图感知（品类/价格约束查询商品优先、促销意图查询有效促销优先）
- **召回前硬过滤**：品牌/品类/价格区间约束先行过滤结构化商品文档，缩小候选集

### 🧠 双层查询理解

- **规则 + 词典层**：品牌、品类、价格区间、月份确定性提取——零延迟、可单测、离线可用，多品牌比较取并集
- **LLM 补充层**：Qwen3-Max 抽取自然语言约束（词典外品牌、口语价格），输出经白名单清洗后与规则结果合并（列表取并集、标量规则优先，LLM 不得推翻确定性提取）；连续失败 2 次自动熔断回退纯规则

### 🔄 知识更新与去重

- **Manifest 增量索引**：文件 hash 比对——未变文件跳过、变化重建、删除下线，每次同步输出可审计统计，重复运行幂等
- **三级去重**：MD5 精确匹配 + SimHash 近似查重（64 位指纹/汉明距离）+ 向量语义去重（可选，余弦阈值）
- **时效控制**：过期/未开始促销自动剔除，易变信息（价格/库存）按更新时间做乘性新鲜度加成（仅作同分排序 tie-breaker，不反转相关性）

### 🛡️ 检索质量门禁

检索结果不直接交给 LLM，先过三信号门禁：

1. **词面信号**：双路召回一致度 + 查询内容词对候选的覆盖率；top-3 内知识/促销文档重排分 ≥ 0.05 时补救放行（覆盖同义改写）
2. **重排置信**：候选分过低且覆盖不足时拒绝；完整短查询与促销意图查询有豁免路径（点名优惠形式的"满X减Y/X折"类查询不豁免）
3. **时效匹配**：查询"N月"活动而 top-1 促销不在该月生效时拒绝

未通过门禁返回明确拒答话术（含转人工提示），`context` 为空，不向生成阶段提供低质量上下文。阈值在 85 条标注集上以生产模型 bge-reranker-v2-m3 校准（无答案查询重排分 ≤ 0.0244 / 可回答 ≥ 0.0631，补救阈值取 0.05）。

### ⚡ 结构化双通路

- **结构化通路**：价格/库存/SKU 查询直接从商品目录生成答案，数字永远不会被模型改写，并自动附带当前有效促销
- **语义通路**：混合检索 → 质量门禁 → 上下文组装 → Qwen3-Max 生成（防幻觉提示词约束：只用资料、无依据拒答、数字不改写、附引用编号）

### 📊 离线评测与工程化

- **消融评测**：85 条人工标注查询（71 可回答 + 14 无答案，10 类标签），Dense / BM25 / Naive-Concat / RRF / Full 五模式同集对比，逐条记录落盘 `reports/`
- **固定技术栈**：嵌入 BGE-M3、重排 bge-reranker-v2-m3、向量库 ChromaDB、会话存储 Redis，评测与线上完全同模型；LLM 未配置或调用失败自动证据直出
- **测试**：76 个单元测试（测试替身隔离模型依赖，无 GPU、无网络环境可复现）

## 🛠️ 技术栈

| 类别 | 技术 | 用途 |
|---|---|---|
| 开发语言 | Python | 主要开发语言 |
| RAG 框架 | LangChain | Qwen3-Max 生成接入（ChatOpenAI → DashScope OpenAI 兼容模式） |
| 向量数据库 | ChromaDB | 语义向量持久化与检索，维度不符自动整库重建 |
| 嵌入模型 | BGE-M3 | 语义向量化，sentence-transformers 加载 |
| 重排模型 | CrossEncoder (bge-reranker-v2-m3) | 候选结果逐对打分精排 |
| 对话模型 | Qwen3-Max | 答案生成与查询约束抽取 |
| 会话存储 | Redis | 多轮会话历史（TTL 7 天 / 上限 50 条），需先启动 Redis 服务 |
| 检索核心 | Python 标准库 + NumPy | BM25 / RRF / 切分 / 去重自研实现，零框架依赖 |
| Web 框架 | Streamlit | 客服界面：问答、检索证据展示、知识库管理、系统状态 |
| 评测 | pytest + 消融脚本 | 76 个单元测试 + 85 条标注集五模式消融 |

> 检索核心自研零框架依赖；单元测试通过测试替身（Test Double）隔离嵌入/重排/LLM 依赖，无 GPU、无网络环境可复现运行。

## 🚀 快速开始

### 环境要求

- Python ≥ 3.10
- Redis（会话存储为 Redis-only，须先启动；Windows 可直接运行 `redis-server.exe` 或以管理员启动 Redis 服务）
- 本地模型：BGE-M3 与 bge-reranker-v2-m3（首次运行自动从 Hugging Face 下载，国内可用 [hf-mirror.com](https://hf-mirror.com) 镜像；已缓存则离线可用，设 `HF_HUB_OFFLINE=1` 跳过联网检查）
- 可选：DashScope API Key（配置后启用 Qwen3-Max 生成与约束抽取；未配置时证据直出，链路完整可用）

### 安装

```bash
git clone https://github.com/Seren-xx/retail-rag-chatbot.git
cd retail-rag-chatbot
python -m venv .venv
# Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -e ".[dev]"        # 最小安装（运行单元测试：76 passed）
pip install -e ".[models]"     # sentence-transformers（本地 BGE-M3 嵌入 / CrossEncoder 重排）
pip install -e ".[vector]"     # chromadb（向量库）
```

按需安装其余可选依赖：

```bash
pip install -e ".[llm]"        # langchain（Qwen3-Max 生成接入）
pip install -e ".[ui]"         # Streamlit 界面
pip install -e ".[redis]"      # Redis 会话存储
pip install -e ".[ingest-pdf]" # PDF 解析与表格抽取（pdfplumber）
pip install -e ".[ingest-docx]" # DOCX 解析与表格抽取（python-docx）
pip install -e ".[ingest-xlsx]" # Excel 解析（openpyxl）
pip install -e ".[all]"        # 全部
```

### 模型配置

生产默认即固定技术栈（BGE-M3 / bge-reranker-v2-m3 / ChromaDB / Qwen3-Max），无需配置即可运行：

```bash
# 生成模型（未配置 Key 时自动降级为证据直出）
export DASHSCOPE_API_KEY="your-key"

# 本地已缓存模型时设离线模式，跳过联网检查（Windows PowerShell: $env:HF_HUB_OFFLINE='1'）
export HF_HUB_OFFLINE=1

# 会话存储 Redis 连接地址（Redis 须已启动）
export REDIS_URL="redis://localhost:6379/0"
```

### 启动 Redis

```bash
redis-server                      # 或以管理员启动系统 Redis 服务；验证：redis-cli ping → PONG
```

### 构建索引

```bash
python scripts/build_index.py     # 构建索引：加载→切分→去重→文档库
                                  # manifest 增量：重复运行只处理变化文件（幂等）
```

### 运行评测

```bash
# 五模式消融评测（生产默认模型，结果写入 reports/，即下方评测表）
python scripts/evaluate_retrieval.py --today 2026-09-11
```

### 启动服务

```bash
streamlit run interfaces/streamlit_app.py   # 客服界面（也可 streamlit run app_qa.py）
```

界面含三个页面：**智能问答**（输入问题，可展开查看路由、约束、检索证据与质量信号）、**知识库管理**（上传文件 → 增量同步）、**系统状态**（模型 / 会话存储 / 索引情况）。

## 📖 模块详解

### 1. 多源知识处理

**多格式接入**：`CSV / JSONL / TXT / Markdown / XLSX` 原生或可选依赖支持，`PDF / DOCX` 经可选依赖启用。

**表格抽取**：所有格式中的表格统一拍平为结构化文本后与正文一起索引——DOCX 表格、Markdown 管道表格、XLSX 工作表（每 sheet 一个文档）、PDF 页面表格（pdfplumber）。两列表按"字段：值"逐行输出，多列表按表头配对，表格信息不再丢失；检索层只消费文本，不为表格维护第二套存储。

**结构化字段入元数据**：CSV 按商品 ID 生成稳定 `doc_id`，价格、库存、品牌、品类写入 `metadata` 供召回前硬过滤与评测；JSONL 促销的生效期写入 `metadata` 供时效过滤。

**语义级切分**：段落优先（一段往往是一个完整语义单元）→ 超长段落按标点分句组块 → 块间 80 字重叠，避免商品说明被固定长度截断。

### 2. 索引与三级去重

索引分两层回答两个不同的问题：

- **Manifest 增量**：记录每个文件的 hash、状态、chunk 数——文件没变直接跳过，变了重新索引，删了自动下线
- **三级去重**（阻止重复内容进入索引）：
  - MD5 精确匹配
  - SimHash 近似查重（字符 bigram 64 位指纹，汉明距离 ≤ 3 判重）
  - 向量语义去重（可选开启，余弦相似度 ≥ 0.85 判重）

文档库（`docstore.jsonl`）是检索的唯一数据源，向量索引从它构建，Chroma collection 元数据记录嵌入维度，切换嵌入模型后自动整库重建。

### 3. 查询理解与双通路路由

**意图路由**：数值关键词 + 正则模式 + SKU 编号判定。价格、库存、规格类查询走结构化通路；促销/优惠列举类查询走语义通路（答案在促销文档，catalog 证据不含促销）。

**约束提取（双层）**：

| 层 | 机制 | 特性 |
|---|---|---|
| 规则 + 词典 | 品牌词典命中、品类同义词表、价格区间正则、月份正则 | 零延迟、可单测、离线可用，多品牌取并集 |
| LLM 补充 | Qwen3-Max 输出 JSON 约束 → 白名单清洗（品类校验/数值范围/月份 1-12）→ 与规则结果合并 | 列表取并集、标量规则优先；未配置 Key 不启用；连续失败 2 次熔断 |

### 4. 混合检索与重排

| 检索方式 | 优势 | 适用场景 |
|---|---|---|
| BM25 | 精确匹配关键词 | 品牌、SKU、专业术语 |
| 向量检索 | 语义相似度匹配 | 口语化表达、同义替换 |

双路结果经 **RRF**（Reciprocal Rank Fusion）按稳定 `doc_id` 融合去重（只用药次不比量纲），再经 **CrossEncoder** 逐对打分精排。排序阶段引入**意图感知**：

- 带品类/价格约束的列举查询：符合条件的商品文档排在无关文档之前
- 促销意图 + 品类/时间明确的查询：有效促销文档排在品类相似的商品之前

### 5. 质量门禁与上下文工程

三信号门禁（阈值在标注集上校准，详见上文核心特性）决定检索结果是否值得交给 LLM。通过门禁的结果经 **Source Balance**（单一来源限额，防止单文件霸屏）与 **Context Packing**（字符预算内打包，保留 `[doc_id]` 前缀供答案引用）组装上下文。

### 6. 答案生成与会话

- **Qwen3-Max 生成**：LangChain `ChatOpenAI` 接 DashScope OpenAI 兼容模式；防幻觉提示词四条约束（只用资料 / 无依据拒答 / 数字不改写 / 附引用编号）
- **三层降级**：未配置 Key → 证据直出；调用失败（限流/网络/额度）→ 降级证据直出；资料无答案 → 提示词约束拒答，与检索层拒答口径一致
- **会话存储**：Redis（`session_id` → List，TTL 7 天自动过期、上限 50 条，损坏数据容错跳过）；生成时携带最近 6 条历史

### 7. 服务化与离线评测

- **Streamlit**：智能问答（含检索证据展开）、知识库管理（上传 → 增量同步）、系统状态
- **消融评测**：`scripts/evaluate_retrieval.py` 五模式（dense/bm25/concat/rrf/full）同一查询集对比，逐条记录（查询、排序结果、门禁决策、质量信号、延迟）落盘 CSV + JSON，bad case 可直接提取分析

| Naive Concat | 0.9413 | 0.9577 | 0.8674 | 0.8827 | 196.1 | 242.2 | - | - |
| Hybrid RRF | 0.9472 | 0.9577 | 0.9225 | 0.9207 | 194.3 | 236.0 | - | - |
| Full（+重排+时效+门禁） | **0.9648** | **0.9718** | **0.9249** | **0.9230** | 5666.8 | 10289.0 | **1.0000** | **0.0000** |

**消融读法**：

- BM25 单路 Recall@5 0.9237 → RRF 融合 0.9472 → 完整链路（+重排+门禁）**0.9648**：每加一个组件的收益都被同一查询集度量
- BGE-M3 语义单路已达 0.9542，RRF 融合后 Recall 略降（0.9472）但 MRR 更高（0.9225 vs 0.9131）；完整链路四项指标全部最高——融合的价值在排序质量与对语义失效查询（SKU/品牌精确匹配）的兜底，而非单点 Recall
- Naive Concat（两路朴素交替、无分数融合）Recall/MRR/nDCG 全面低于 RRF（Hit@5 持平），证明**融合策略本身**有贡献，不只是"多路"
- 14 条无答案查询全部被门禁拒绝（拒答准确率 100%），71 条可回答查询零误拒
- 延迟构成：无重排路径 P95 ≈ 236ms（其中 BGE-M3 查询嵌入约 190ms）；Full 的 P95 ≈ 10.3s 来自 CPU 上 bge-reranker-v2-m3 对 30 候选的逐对重排，GPU 环境可显著降低

**评测暴露并修复的三类真实问题**（逐条记录直接驱动修复，均有单测防回归）：

| Bad Case | 根因 | 修复 |
|---|---|---|
| "九月乳制品有什么优惠"误路由到结构化目录，答案缺失 | "优惠"在数值关键词表，促销列举查询答案在促销文档 | 路由收窄：优惠/促销/满减/打折等从数值关键词移除 |
| "乳制品优惠"首位被品类相似的商品文档挤占 | CrossEncoder 只看语义相似，不懂意图 | 意图感知排序：促销意图 + 品类明确时促销文档提升 |
| 同义改写查询（"钱几天到账" vs 文档"退回"）被词面信号误杀 | 词面覆盖不足即拒绝，误伤有效改写 | 双补救路径：top-3 知识/促销文档重排分 ≥ 0.05 放行 |

## 📈 性能优化

**检索优化**

- 约束硬过滤先行：品牌/品类/价格在召回前过滤结构化商品文档，避免无关候选进入融合与重排
- RRF 只用名次不用分数：规避 BM25 分数与余弦相似度量纲不可比问题，无需调权
- 增量索引：文件级 hash 比对，知识更新只处理真正变化的文件，避免全量重建
- 向量库持久化复用：ChromaDB collection 与文档库 doc_id 对齐时直接复用，doc_id 集合变化才增量 upsert

**延迟档位**

- 无重排路径 P95 ≈ 236ms（BM25 + BGE-M3 向量 + RRF + 门禁全链路，其中 BGE-M3 查询嵌入约 190ms，可缓存查询向量进一步压缩）
- CrossEncoder 路径 P95 ≈ 10.3s（CPU，bge-reranker-v2-m3 对 30 候选逐对重排）；GPU 环境可显著降低，或调小 `rerank_top_k` 控制延迟

**推理与生成优化**

- 规则路由分流：价格/库存等数值查询直接走结构化目录，不占用检索与生成资源
- LLM 约束提取熔断：连续失败 2 次自动停用，后续查询纯规则提取，保证延迟稳定
- 上下文预算控制：字符预算 + 单源限流，控制生成侧 token 消耗与单一来源霸屏
- 生成降级不阻塞：LLM 调用失败立即降级证据直出，链路不中断

**测试**

- 76 个单元测试覆盖路由、约束提取（含 LLM 清洗合并与熔断）、检索、门禁、上下文组装、ChromaDB 维度重建、会话存储（Redis 后端），通过测试替身隔离模型依赖，本地无 GPU、无网络即可复现

## 🎯 应用场景

| 场景 | 示例 | 处理方式 |
|---|---|---|
| 商品事实查询 | `S001 多少钱` | 结构化目录确定性回答，数字来自商品表 |
| 条件列举 | `50元以下的乳制品有哪些` | 品类/价格硬过滤 + 商品文档优先 |
| 商品属性/政策 | `花生过敏能吃花生巧克力吗` | 混合检索 + 质量门禁 |
| 促销时效 | `九月乳制品有什么优惠` | 有效期过滤 + 时效匹配检查 |
| 范围外问题 | `你们和山姆超市什么关系` | 质量门禁拒答，转人工提示 |

## ⚠️ 边界与说明

- 示例数据规模有限（38 篇活跃文档、85 条标注查询），指标结论适用于同规模知识库，不应外推为线上效果
- 评测与生产使用同一套本地模型（BGE-M3 + bge-reranker-v2-m3，本机缓存离线可复现），更换嵌入/重排模型后需重跑评测校准门禁阈值（rerank_rescue / rerank_floor）
- 生产部署还需补充鉴权、限流、监控、日志采样与更大规模标注集
